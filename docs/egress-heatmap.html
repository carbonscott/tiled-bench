How the numbers are computed
The harness records only what it measured. Every rate below is derived here, at build time, from those raw counts -- nothing is stored pre-divided.
NumberEquationReading it
payload_mbps payload_mb / wall_s rate of data you actually wanted
wire_mbps wire_mb / wall_s rate of bytes on the network
ent_per_s entities / wall_s entities delivered per second
app_frac app_sum_s / (wall_s * streams) share of worker-time spent in server work
waste factor wire_mb / payload_mb 1.0 = moved exactly what you needed

streams = threads * processes. wall_s is the timed region only: building clients, listing entity keys and warmup all happen outside it. app_sum_s is the server's own Server-Timing: app;dur summed over every data request; wire_mb is the sum of HTTP Content-Length. MB = 106 bytes throughout, so an entity labelled 1 MB is really 1.048576 MB.

app_frac only means "who is the bottleneck" while wall time is still improving. Once more threads stop reducing wall_s, every extra thread inflates the denominator with idle time and app_frac falls no matter what the server does. In the c=32 rows the server is working more than twice as hard as at c=8 while app_frac reports it three times less busy. Past that knee, read app_sum_s directly: rising while wall_s is flat means the server is queueing.

payload for raw_export and asset_bytes is imputed. Those two never decode anything, so the harness reports payload_mb = 0. Here it is filled in as entities * mb_per_entity -- the data you asked for, whether or not it was parsed -- otherwise both methods are invisible on a payload chart and their crossover with container_export cannot be seen. Their wire_mb is measured, not imputed.
