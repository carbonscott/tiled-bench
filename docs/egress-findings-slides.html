Step 2 · why export wins serial work measured · remote, n=200, 1 MB/entity

Export pays per entity; read pays per artifact.

Whole-entity fetch, artifact count 1 → 16 at constant entity size. artifact_read spends ~190 ms of navigation (2 metadata GETs + 1 data GET) on every artifact; export ships the entity in one chunked request.

The catch: wire waste

  • Exporting one artifact still ships all of them: waste factor = artifact count (4.0×, 16.3× measured).
  • Extreme case, mixed entity (16.7 MB primary + 64 KB aux): exporting one aux moves 259× the requested bytes — the one serial cell artifact_read wins.

Useful nulls

  • Artifact count does not change single-artifact read latency at all.
  • With the broker mimetype, layout no longer moves method cost (batched ≈ grouped ≈ per_entity at 4 artifacts).
Step 3 · subset vs whole backing file measured · remote, k = 1…1000

Above a crossover fraction, stop selecting — take the whole file.

Fetching k of N entities costs per-entity time; asset_bytes pulls the whole backing file at wire speed, flat in k (1.05 GB ≈ 12.7 s regardless). The crossover fraction is the portable number:

Dataset (shared file)filewhole-file flatcrossover vs exportvs artifact_read
1000 × 1 MB, 1 artifact1.05 GB12.7 s43% (k≈433)7% (k≈67)
256 × 16.8 MB, 1 artifact4.3 GB52.9 s66% (k≈170)45% (k≈116)
1000 × 1 MB, 4 artifacts1.05 GB13.0 s23% (k≈232)2% (k≈19)
1000 × 1 MB, grouped layout1.05 GB13.7 s41% (k≈406)7% (k≈67)

Two knobs move it

  • Entity size pushes it up — export amortizes better on big entities (43% → 66%).
  • Artifact count pulls it down — export pays per artifact, the file doesn't (43% → 23%).

Rules of thumb

  • ~1 MB single-artifact: whole file above ~40%. Big (≥16 MB): export until ~2/3. Multi-artifact: whole file above ~1/4.
  • per_entity layout: no crossover exists — export leads at every k.
Step 6 · the mimetype regression control measured · same files, only the registered mimetype differs

The broker adapter is the difference between usable and broken.

The stock HDF5 adapter re-reads the whole backing file for every entity slice. The broker mimetype (application/x-hdf5-broker) slices lazily.

stock, remote 4.82 s/entity 26× slower
broker, remote 0.186 baseline

artifact_read on batched 1 MB entities. Local: 7× (1.38 → 0.193 s/entity).

Un-broken outright

Whole-dataset export of the 4.3 GB batched set 504'd on every chunk under stock. Broker: 839 MB in ~16 s through the proxy.

Not just a batched concern

Stock taxes per_entity container export too: 60 vs 36 ms/entity remote (~1.7×). Register everything with the broker mimetype.

  • Threads help to c≈8, then plateau with app_frac → 0.07 — the GIL, not the server: 54% of wall samples sit in httpx response-body handling (SSL decrypt + chunk assembly hold the GIL; socket waits release it).
  • raw_export ≈ asset_bytes (+5% serial, nil across processes) — quote the public API to users. Both moved byte-identical wire totals.
  • But raw_export cannot run in a thread pool at all: tiled.client.download.download() installs a SIGINT handler unconditionally → ValueError off the main thread (all releases through 0.2.14). Scale it by process.

Upstream-worthy observations

Guard the signal handler with a main-thread check · whole-array .read() routes through a full dask task graph (pure overhead) · response streaming could release the GIL more (e.g. recv_into a preallocated buffer).

Bandwidth is not the constraint

  • Whole-file streams: 941 MB/s @ 16 → 1197 MB/s @ 32, zero errors.
  • 16 MB asset fan-out: clean to 1040 MB/s @ 128 procs (the Aug-3 era 500'd at ≥16).
  • /healthz fabric: 6300+ req/s — proxy/TLS/routing has ~30× headroom; the catalog path is the limit.

What it means

  • Doubling workers bought 1.6× — worker count is not the serialized resource. Next suspects: Postgres query capacity, per-worker event loop, ingress.
  • Capacity rule: every workload's ceiling = 20 ÷ slot-seconds per unit. Present ≈20 concurrent requests; more only queues.

Side finding — registration race: concurrent registration at pool=8 leaves structure-less "broken" entities, scaling with artifact count (up to 5% on 16-artifact datasets). Damage is invisible to len(dataset) — verify per-artifact. Registering at pool=4 produced zero failures.

Operational guidance · carry this

Rules to carry.

For users of tiled-test

  • Serial work: container_export wins everything except tiny-artifact-of-huge-entity.
  • Batches from shared files: whole-file asset_bytes above the crossover (~40% / ~2/3 / ~1/4 — 1 MB / big / multi-artifact).
  • Bulk: ~8 threads, then processes (~190 MB/s each). Whole-file streaming scales to 32+; request-shaped load saturates at ≈20 concurrent.
  • Never parallelize multi-GB exports — above a few GB use asset_bytes: faster and memory-flat.
  • On-cluster ML pipelines: Mode A / h5py_direct, 1.2–1.5 GB/s.

For admins

  • The ~20-slot serialized resource is the knob worth finding — workers ×2 bought only 1.6×; suspects: DB query capacity, event loop, ingress.
  • Pooler must fit tiled's persistent pools: session mode needs pool ≥ workers × (pool+overflow); transaction mode only on PgBouncer ≥ 1.21 with max_prepared_statements.
  • Run tiled catalog init/migrations direct to Postgres, never through the pooler.
  • Per-pod memory allows ~2 concurrent whole-dataset exports (~9–17 GB); OOMKilled event 2026-08-12 00:12 UTC confirms the exact limit.
  • Storage is never the constraint: one node pulls 2+ GB/s cold from Weka — every HTTP ceiling sits ≥4× below it.
